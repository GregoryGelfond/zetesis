Module resource_limits 

Source
Expand description

The limit each typed resource is counted against, set by resource, for the limits an admission takes and for those of three other operations whose tests span crates.

A refusal at a limit reports the resource it met. The view holds a family of limits when a zetesis-themelios admission takes it, directly or nested in the limits it takes: the admission of a source, of a bundle or of a logical program, formula preparation and expansion included. Those are the formula and expansion resources; the input limits of a source or a bundle; the core admission resources of a source or a logical program, and the logical program resources; the observation and objective admission resources; and the aggregate ceilings an aggregate error kind reports. Formula admission counts template variables and predicate arity against the core admission limits, so those two formula resources are set through admission_formula.

The view also holds the limits of three operations other than admission, because the tests of more than one crate set them one at a time: loading a bundle (bundle_loading), building an objective plan (objective_plan), and evaluating an admitted program’s observations (observation_evaluation). Evaluation counts Nodes, Depth and Bytes per constructed symbol against fields of its own, while observation() pairs those three resources with their admission fields and refuses the resources counted only while observations are evaluated.

The limits of operations that only one crate’s tests set are paired in that crate’s tests/integration/support. In zetesis-themelios these are compiling a program’s metadata through its own door (metadata_resources), planning counts (count_plan_resources), bounding an objective (objective_bound_resources, which sets its aggregate ceilings through aggregate), and constructing observation symbols (observation_construction).

The view stands above zetesis-themelios, so it serves the tests that use that crate as a dependency, its own integration tests among them. A unit test of zetesis-themelios would link a second copy of the crate, and a test of a crate below it would make that crate depend on its own dependents, so the tests of the crates that define these limits (the unit tests of zetesis-themelios, and the tests of zetesis-core, zetesis-ferraris and zetesis-objective) name the fields they set themselves. The view’s own tests check that each resource it names has a field of its own; that the field is the one a refusal reports is checked only where a test the view serves meets that refusal.

A test the view serves that sets one such limit, leaving the others at their defaults, names the resource; the field holding that limit is named here, once. A test that sets several limits at once, or varies one limit of a configuration that already sets others, names the fields, and its code shows why. A test that sets a field of these limits that no typed resource reports, such as the formula limits’ key-analysis work, says why where it sets it. Formula and expansion limits are also read by resource, so a threshold search over one of them starts from its default. Limits are read and set as u64 whatever the field’s width.
